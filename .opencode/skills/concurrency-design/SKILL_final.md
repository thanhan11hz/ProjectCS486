## 4. Discovery Process

The discovery process outlines the deep technical analysis required before writing the document.

### Step 4.1: Analyze the Database Engine
Acknowledge that the target engine is Microsoft SQL Server. This means your solutions must utilize concepts native to SQL Server.
* **Isolation Levels:** `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`, `SNAPSHOT`.
* **Locking Hints:** `WITH (UPDLOCK)`, `WITH (XLOCK)`, `WITH (ROWLOCK)`, `WITH (NOLOCK)`.
* **Row Versioning:** `READ_COMMITTED_SNAPSHOT` (RCSI).

### Step 4.2: Analyze Each Conflict (CC-01 to CC-05)
For each conflict, determine the lowest-impact mechanism that completely prevents the race condition.

* **CC-01 & CC-02 (Booking Overlaps):** Checking for overlapping time ranges is a classic "phantom read" problem. If you use `READ COMMITTED`, a second transaction can insert a booking into the range you just checked before you commit your own insert. Therefore, `SERIALIZABLE` isolation is typically required to prevent phantom inserts in range queries. Alternatively, a pessimistic locking approach on a parent resource (like the Space record) using `UPDLOCK` could serialize access to that specific room. Evaluate and choose the best approach.
* **CC-03 (Escalation vs Booking):** Escalating a maintenance record to `out_of_service` must prevent new bookings and identify existing ones. This requires serializing access between the maintenance update and the booking creation for that specific space.
* **CC-04 (Advisory Miss):** A booking must capture all active advisories. This is a read-then-write scenario. Using `SNAPSHOT` isolation might result in a write-skew anomaly. Using an `UPDLOCK` on the space's maintenance records during the booking transaction ensures no new advisories can be committed until the booking is finalized.
* **CC-05 (Concurrent Maintenance Updates):** Two staff updating the same record is a classic lost-update problem. An `UPDLOCK` on the `SELECT` prior to the `UPDATE`, or optimistic concurrency using a `rowversion` column, are appropriate SQL Server solutions.

## 5. Concurrency Design Rules

The following rules define the strict standards the output document must adhere to.

### Rule C1 — Template Adherence
You MUST strictly follow the structure defined in `concurrency-design-template.md`. Copy the headers exactly. Fill in the specific bullet points: Scenario, Shared Resource, Business Rule Protected, Chosen Mechanism, Implementation Pseudo-code, and Justification.

### Rule C2 — Specific SQL Server Mechanisms
Generic answers ("use a transaction") will result in failure. You must name the exact SQL Server feature.
* Example of acceptable mechanism: "Transaction with `SERIALIZABLE` isolation level."
* Example of acceptable mechanism: "Pessimistic concurrency using `WITH (UPDLOCK, ROWLOCK)`."

### Rule C3 — Rigorous Justification
Every chosen mechanism must be justified by explicitly referencing the Business Rule it protects.
* You must explain *why* a weaker mechanism would fail. For example, explain why `REPEATABLE READ` is insufficient for CC-01 because it doesn't prevent phantom inserts.
* You must explain *why* your chosen mechanism is optimal for performance (e.g., explaining that locking the parent Space record is better than locking the entire Bookings table).

### Rule C4 — Valid T-SQL Pseudo-code
Provide pseudo-code demonstrating the transaction boundary and locking strategy.
* Use `BEGIN TRAN` and `COMMIT TRAN`.
* Show where `TRY...CATCH` blocks would handle deadlocks or constraint violations.
* If using table hints, show the exact syntax: `SELECT * FROM Bookings WITH (UPDLOCK) WHERE...`
