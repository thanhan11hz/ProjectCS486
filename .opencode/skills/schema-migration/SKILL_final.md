## 4. Discovery Process

The discovery process outlines the analytical steps required before writing the SQL script.

### Step 4.1: Analyze the Baseline and Constraints
Read the `05-db-implementation-G7.sql` file. Look specifically for `CHECK` constraints on the `bookings` and `spaces` tables related to maintenance. In Phase 1, any maintenance blocked a booking. Note the exact names of these constraints (e.g., `ck_bookings_maintenance_conflict`).

### Step 4.2: Analyze the Delta
Read the Phase 2 analysis. Understand that `impact_level` determines booking availability. 
* `out_of_service` blocks bookings.
* `advisory` allows bookings but requires notification.
Therefore, the old blanket "no maintenance allowed" constraints from Phase 1 must be surgically removed.

### Step 4.3: Plan Data Type Mapping
* `impact_level`: This is an enumerated string. `VARCHAR(20)` is appropriate. It is a mandatory field (`NOT NULL`).
* `advisory_acknowledged`: This is a boolean. `BIT` is appropriate. It is conditionally nullable, so the column itself must allow `NULL` at the schema level.

## 5. Migration Implementation Rules

The following rules define the strict standards the output script must adhere to.

### Rule M1 — Strict Idempotency
Every single DDL operation must be wrapped in an existence check. The script must be capable of being run 100 times in a row without producing a single SQL error.

**Pattern for Adding Columns:**
```sql
IF NOT EXISTS (
    SELECT 1 FROM sys.columns 
    WHERE Name = N'column_name' 
    AND Object_ID = Object_ID(N'table_name')
)
BEGIN
    ALTER TABLE table_name ADD column_name data_type;
END
GO
```

**Pattern for Dropping Constraints:**
```sql
IF EXISTS (
    SELECT 1 FROM sys.check_constraints 
    WHERE name = N'constraint_name' 
    AND parent_object_id = Object_ID(N'table_name')
)
BEGIN
    ALTER TABLE table_name DROP CONSTRAINT constraint_name;
END
GO
```

### Rule M2 — Safe NOT NULL Addition
Adding a `NOT NULL` column to a populated table causes a fatal error in SQL Server unless a default is provided. 
If `impact_level` is `NOT NULL`, you must use the following pattern:
1. Add the column with a `DEFAULT` constraint to populate existing rows (e.g., default to 'advisory' or 'out_of_service' depending on business logic assumption).
2. Explicitly drop the default constraint immediately afterward so that future `INSERT` statements are forced to provide the value explicitly.

**Pattern:**
```sql
IF NOT EXISTS (SELECT 1 FROM sys.columns WHERE Name = N'impact_level' AND Object_ID = Object_ID(N'maintenance_records'))
BEGIN
    -- 1. Add column with a temporary default
    ALTER TABLE maintenance_records ADD impact_level VARCHAR(20) NOT NULL CONSTRAINT df_maintenance_records_impact_level DEFAULT 'out_of_service';
    
    -- 2. Drop the temporary default constraint
    ALTER TABLE maintenance_records DROP CONSTRAINT df_maintenance_records_impact_level;
END
GO
```

### Rule M3 — Constraint Addition and Naming
When adding `CHECK` constraints for the new domain values, use `IF NOT EXISTS` and adhere to the Phase 1 naming convention (`ck_<table_name>_<column_name>`).

**Pattern:**
```sql
IF NOT EXISTS (SELECT 1 FROM sys.check_constraints WHERE name = N'ck_maintenance_records_impact_level')
BEGIN
    ALTER TABLE maintenance_records ADD CONSTRAINT ck_maintenance_records_impact_level CHECK (impact_level IN ('out_of_service', 'advisory'));
END
GO
```

### Rule M4 — Cleanup of Obsolete Logic
Identify the constraints in `05-db-implementation-G7.sql` that enforce BR-19 (no overlapping maintenance) and BR-33 (all maintenance blocks bookings). Write `IF EXISTS ... DROP CONSTRAINT` statements for them, as they contradict the new Phase 2 rules.
